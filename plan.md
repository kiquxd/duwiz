# План: превью файлов

## Зачем это нужно и какой вариант выбрать

Превью нельзя делать прямо из callback-а FTXUI, который рисует меню. Рендерер
вызывается много раз: чтение файла, определение MIME-типа или декодирование
изображения внутри него будут подвешивать интерфейс.

Есть три реалистичных подхода:

1. **Запускать внешние программы** (`file`, `bat`, `chafa`) — это самый короткий
   путь по количеству собственного кода, но он требует запускать shell-процессы,
   парсить их вывод, плохо отменяется и может ломать экран FTXUI escape-
   последовательностями. Для этого проекта не подходит.
2. **Поддержать только текст и hex-дамп** — хороший маленький первый релиз.
   Нужны только POSIX-вызовы для чтения файла и FTXUI для вывода строк.
3. **Сделать нормальное in-process превью** — рекомендуемый вариант. Текст и
   binary обрабатываются собственным небольшим кодом, тип определяется
   `libmagic`, а изображения проходят через GdkPixbuf и Chafa. Кода заметно
   больше, но не нужны внешние процессы, UI остаётся отзывчивым, а компоненты
   можно расширять независимо.

Дальше описан третий вариант. Его стоит делать поэтапно: после этапа с
текстом/hex уже будет полезное превью, а изображения можно добавить позже.

## Что следует поправить в текущем наброске

- Убрать `exec_command` с `popen`: для превью он не нужен.
- Не вызывать `getFileType` из `MenuOption::transform`. Этот callback должен
  только описывать внешний вид строки; в нём нельзя читать диск и менять
  состояние приложения.
- Не хранить `ftxui::Elements` как результат превью и не передавать их через
  `std::move` в рендерер. Результат нужно хранить в виде данных: строк, байтов
  hex-дампа или массива ячеек изображения. FTXUI-элемент строится заново из этих
  данных при отрисовке.
- Ошибки определения типа не писать в `stderr`: fullscreen-TUI может от этого
  визуально испортиться. Ошибка должна попасть в статус превью.
- Перед началом работы с превью закончить переделку `ThreadPool` на очередь с
  `condition_variable`. Нынешний busy-loop будет тратить CPU и ухудшит
  отзывчивость даже при отдельном preview-потоке.

## Как выглядит результат для пользователя

При перемещении курсора справа сразу появляется название и статус `Loading…`.
Через короткую паузу появляется один из вариантов:

- каталог: тип, права, размер и данные из уже имеющегося size-кэша;
- симлинк: сам факт симлинка и его target, без неявного перехода по нему;
- текстовый файл: первые строки, с сохранением отступов;
- бинарный файл: компактная таблица «смещение / hex / printable ASCII»;
- изображение: масштабированная цветная терминальная миниатюра;
- неподдерживаемый файл: MIME-тип, размер и понятная подпись, без попытки
  открыть его неподходящим обработчиком.

При быстром перемещении по списку не должно быть мерцания от старых результатов
и задержки реакции на клавиши.

## Модель данных и границы ответственности

Нужен отдельный объект состояния превью, например `PreviewData`. Его задача —
хранить только данные, которые можно безопасно передать между потоками:

- путь и идентификатор файла;
- статус: загрузка, готово, недоступно, ошибка;
- базовые метаданные: тип объекта, права, размер, MIME;
- один из payload-ов: текстовые строки, строки hex-дампа или массив ячеек
  изображения (символ, foreground, background).

Сам рендерер берёт готовый `PreviewData` и создаёт FTXUI-элемент. Он не делает
I/O, не меняет данные и не запускает вычисления.

Полезно заранее ввести номер запроса — возрастающий `generation id`. Каждый раз
при смене выделения номер увеличивается. Если worker закончил старое задание, UI
сравнивает его номер с текущим и просто выбрасывает устаревший ответ.

## Поток для превью

Для превью стоит выделить один отдельный `std::jthread`, а не класть задачи в
пул подсчёта размеров каталогов.

Почему именно один:

- одновременно пользователь видит лишь одно превью;
- приоритет у новой выбранной строки всегда выше старой;
- декодирование крупного изображения не задержит переход по каталогам;
- одна очередь и один владелец `libmagic` заметно проще в отладке.

Почему `std::jthread`, а не голый `std::thread`:

- он автоматически делает `join` при уничтожении объекта;
- у него есть `stop_token` для штатного завершения;
- не нужно помнить о ручном `join` во всех ветках выхода из приложения.

Документация: [std::jthread](https://en.cppreference.com/w/cpp/thread/jthread),
[std::stop_token](https://en.cppreference.com/w/cpp/thread/stop_token),
[std::condition_variable](https://en.cppreference.com/w/cpp/thread/condition_variable).

### Поведение очереди

Очередь превью не должна быть обычной FIFO из сотен запросов. Достаточно
хранить один pending-запрос:

1. Пользователь выделяет файл — запрос записывается как pending.
2. Если пользователь тут же выделяет следующий, pending-запрос заменяется.
3. Worker ждёт на `condition_variable`, забирает последний запрос и начинает
   работу.
4. Уже выполняющийся запрос не обязательно физически отменять: по завершении
   его результат будет проигнорирован по `generation id`.

Перед запуском задания стоит подождать примерно 50–100 мс. Это debounce:
быстрое нажатие стрелок не будет запускать обработку каждого промежуточного
файла.

Worker не должен создавать или изменять FTXUI-компоненты. Он кладёт готовые
данные в защищённое состояние и отправляет в главный цикл `Event::Custom`.
FTXUI документирует этот способ как thread-safe для запроса перерисовки:
[Force a frame redraw](https://arthursonzogni.github.io/FTXUI/module-component.html).

## Безопасное чтение файлов

Не следует открывать файл через `FILE*`, `ifstream` или `magic_file` без
проверки типа объекта. На Linux лучше использовать небольшой RAII-класс для file
descriptor и системные операции `openat`, `fstat` и `pread`.

1. Открыть выбранный entry с close-on-exec и без неявного следования симлинку.
2. Проверить descriptor через `fstat`.
3. Читать содержимое только у обычных файлов.
4. Для FIFO, сокетов, устройств и каталогов показывать только метаданные.
   Иначе можно повиснуть на чтении pipe или получить непредсказуемое поведение.
5. Читать строго ограниченный объём данных через `pread`, не весь файл.

Для первого релиза достаточно таких лимитов:

- текст: 64 KiB, не более 200 строк, каждая строка ограничена по ширине панели;
- binary: 512–1024 байта;
- изображения: сначала получить размеры, затем не принимать файлы с слишком
  большим числом пикселей, например более 40–80 миллионов.

`mmap` для превью не требуется: файлы малы в рамках лимита, а обработка
изменяющегося файла станет сложнее.

Справка по системным вызовам: [open(2)](https://man7.org/linux/man-pages/man2/open.2.html),
[fstat(2)](https://man7.org/linux/man-pages/man2/fstat.2.html),
[pread(2)](https://man7.org/linux/man-pages/man2/pread.2.html).

## Определение типа файла

`libmagic` подходит для выбора обработчика, но его handle не нужно создавать
при каждом выделении файла. Один handle создаётся и загружается вместе с
preview-worker, после чего переиспользуется.

Предпочтительно определять тип по уже открытому file descriptor через
`magic_descriptor`: это не требует повторно открывать путь и уменьшает число
гонок, когда файл переименовали или удалили между выбором и обработкой.

Документация: [libmagic / magic_descriptor](https://www.man7.org/linux/man-pages/man3/magic_descriptor.3.html).

MIME — подсказка, а не единственный источник истины. Для выбора text/binary
нужно также смотреть на первые байты: NUL-байт и невалидный UTF-8 — основания
показать hex-дамп, а не пытаться передать мусор в FTXUI `text`.

## Текстовый и binary preview

Это стоит сделать раньше изображений: зависимостей почти нет, а польза
немедленная.

### Текст

- Валидировать UTF-8 перед передачей строк в FTXUI.
- Разбивать ограниченный буфер на строки, не терять ведущие пробелы и табы.
- Обрезать длинные строки с многоточием; не делать переносы, если превью
  задумано как просмотр кода/логов.
- Показывать внизу пометку, что показано только начало файла, если достигнут
  лимит чтения.

Подсветку синтаксиса лучше оставить на потом. Если она понадобится, разумный
вариант — tree-sitter плюс небольшой собственный слой цветов, но это не нужно
для жизнеспособного первого варианта.

### Binary

Достаточно 16 байтов в строке: offset, шестнадцатеричные байты и printable ASCII
справа. Такой формат универсален, дешёв и намного честнее, чем попытка показать
невалидные данные как текст.

## Изображения

Chafa уже добавлена в зависимости, но важно разделить её роль: Chafa превращает
готовые пиксели в символы терминала, **она не является универсальным загрузчиком
изображений**. Нужен декодер.

Для этого проекта наиболее практичен GdkPixbuf:

- он загружает распространённые форматы;
- умеет потоковую загрузку и масштабирование;
- хорошо сочетается с уже подключённым GLib;
- после декодирования даёт RGB/RGBA-буфер, который можно отдать Chafa.

Нужно добавить пакет и `pkg-config`-зависимость `gdk-pixbuf-2.0` в скрипт
установки, Dockerfile и Makefile. Его API: [GdkPixbuf](https://docs.gtk.org/gdk-pixbuf/),
[PixbufLoader](https://docs.gtk.org/gdk-pixbuf/class.PixbufLoader.html).

Алгоритм обработки изображения:

1. Узнать ширину и высоту, применить лимит на количество пикселей.
2. Вычислить размер preview-панели в символах с учётом текущего терминала.
3. Декодировать и уменьшить изображение до этого размера, сохранив пропорции.
4. Передать RGB/RGBA-пиксели в `ChafaCanvas` нужной геометрии.
5. Забрать из Chafa для каждой ячейки символ, foreground и background.
6. Сохранить эту маленькую сетку в `PreviewData`.

Нельзя брать результат `chafa_canvas_print()` и класть его в `ftxui::text`:
это ANSI-escape-последовательности для прямой печати в терминал, а FTXUI владеет
своим экраном и не должен получать сырой ANSI-вывод. Нужны ячейки через API
Chafa `get_char_at` и `get_colors_at`.

Справка: [ChafaCanvas](https://hpjansson.org/chafa/ref/chafa-ChafaCanvas.html).

В UI эти ячейки нужно переложить в FTXUI Canvas или маленький собственный DOM
node. FTXUI Canvas умеет работать с символами и цветными ячейками; у него есть
свои соотношения пикселей и терминальных ячеек, их нужно учесть при адаптации.
Документация: [FTXUI Canvas](https://arthursonzogni.github.io/FTXUI/canvas_8hpp_source.html).

Если когда-нибудь основной задачей станут гигапиксельные изображения, RAW или
TIFF, имеет смысл отдельно рассмотреть libvips. Для обычного файлового браузера
GdkPixbuf с ограничением размеров проще в поддержке и достаточно эффективен.

## Кэш

Кэш полезен, чтобы при возвращении на строку не читать и не декодировать файл
повторно. Ключ кэша должен содержать не только путь, но и device, inode, mtime,
размер файла и размеры preview-панели. Тогда rename не создаст ложное превью, а
изменённый файл или resize терминала получат новый результат.

Кэш нужно ограничить по памяти, например 8–32 MiB, и вытеснять давно не
использованные результаты. Для изображений кэшировать терминальную сетку, а не
оригинальный bitmap.

## Порядок реализации

1. Закончить блокирующую очередь и штатную остановку существующего ThreadPool.
2. Убрать `popen` и синхронный `libmagic` из рендерера. Добавить справа простой
   блок статуса превью.
3. Ввести `PreviewData` и синхронно реализовать метаданные, text и hex для
   маленьких файлов. Это удобная контрольная точка: UI должен оставаться чистым
   и предсказуемым.
4. Добавить `PreviewService` с одним `std::jthread`, debounce, generation id и
   отправкой `Event::Custom` в UI.
5. Добавить LRU-кэш и обработку удаления/переименования выбранного файла во
   время фонового запроса.
6. Подключить GdkPixbuf, добавить проверку размеров изображения и сделать
   Chafa-to-FTXUI адаптер.
7. Протестировать и только потом добавлять новые форматы: архивы, PDF, аудио,
   видео. Для них нужны прямые библиотеки, а не запуск внешних программ:
   соответственно libarchive, Poppler, TagLib или libavformat.

## Что проверить вручную и тестами

- Быстро двигать курсор по тысяче файлов, включая крупные изображения: интерфейс
  не должен подвисать и показывать результат от старого файла.
- Проверить пустой файл, очень длинную строку, невалидный UTF-8, файл с NUL,
  большой binary-файл, недоступный файл и удаление файла во время загрузки.
- Проверить симлинк, FIFO и `/proc`-подобные файлы: программа не должна
  блокироваться на чтении.
- Проверить битые и чрезмерно большие изображения.
- Изменить размер терминала: текст должен корректно обрезаться, а изображение —
  перерисовываться в подходящей геометрии.

## Критерий готовности

Функция считается готовой, когда она показывает полезное превью текстов,
binary-файлов и изображений, не запускает внешних команд, не читает специальные
файлы, не делает тяжёлой работы в UI-потоке и не снижает отзывчивость навигации.
